# 曲库有序可靠性与可维护性加固设计

## 背景

曲库有序 2.0.8 已完成界面统一、镜像发布与资源占用治理。当前部署的空闲 CPU 占用和约 58MB 常驻内存均合理，Plex 写入也已经具备归属标记、指纹、回读确认、快照和用户隔离保护。本轮工作不重做已经稳定的业务，而是处理审计中确认的长期风险：调度器缺少自恢复、临时失败重试不统一、登录会话不是事务化存储、状态轮询读取过重、样式覆盖层过多，以及少量历史兼容结构继续扩大维护成本。

## 目标

- 一次非致命异常不能永久终止自动任务调度。
- 自动任务区分临时故障和安全故障，临时故障有限重试，安全故障继续保持暂停和人工核对。
- 管理员会话的创建、撤销和全部撤销具备数据库级原子性。
- 高频状态轮询不再反复加载全部歌曲学习状态。
- 运行状态能真实反映调度器存活、最近轮询、最近异常和下一次重试。
- 前端保持 2.0.8 已认可的视觉效果，以播放列表页面的排版、色彩和主题适配为基准，减少重复覆盖规则。
- 拆除已经没有生产调用的历史代码，并将过长入口拆成职责清楚的模块。
- 升级保持向后兼容，不丢失登录、配置、学习记录、歌单托管记录或回滚快照。

## 非目标

- 不重写推荐算法，不改变每日推荐、智能歌单或主题歌单的选择策略。
- 不改变 Plex 歌单归属判断、写入前确认、写入后回读或回滚规则。
- 不更换 FastAPI、SQLite、原生 JavaScript 或现有部署方式。
- 不重新设计用户已经确认的界面，不引入新的前端框架。
- 不以降低当前约 58MB 内存为目标；本轮性能工作面向规模增长和轮询成本。

## 方案选择

采用渐进式加固，而不是全面重写。

全面重写能够获得最整齐的目录，但会同时改动调度、数据迁移、推荐和页面，回归风险不合理。只修调度器虽然最快，却会保留状态接口、会话和 CSS 的已知债务。本方案按独立边界逐项替换，每一步都有迁移测试和兼容入口，任何一项失败都可以单独回退。

## 一、自动任务监督与健康状态

### 调度监督器

`ProfileRuntime` 继续保持单一串行调度器和全局任务门。新增一个显式的运行状态对象，至少包含：

- `started_at`
- `heartbeat_at`
- `last_cycle_started_at`
- `last_cycle_finished_at`
- `last_error_at`
- `last_error`
- `consecutive_failures`
- `alive`

调度循环每次开始和结束都更新状态。`run_due()` 外围由监督器捕获 `Exception`，记录经过脱敏的错误，然后继续下一轮，不能因为一次数据库、迁移或上游异常退出线程。`BaseException` 不捕获，保证进程退出、解释器中断等系统行为仍可生效。

Web 生命周期保存调度线程引用。关闭时设置停止事件、唤醒线程并在有限时间内 `join`，避免测试、升级或容器退出时残留不明确状态。生命周期清理使用 `try/finally`，即使应用关闭过程出现异常也会执行。

### 错误分类与重试

自动任务采用三类结果：

1. `success`：正常推进到下一个计划周期。
2. `deferred` 或 `transient_error`：保留原计划槽位并进行有限重试。
3. `safety_error`：不盲目重试；由现有保护逻辑暂停相应功能并提示人工核对。

网络超时、连接失败、HTTP 429、上游 5xx 和暂时无数据属于临时故障。Plex 身份变化、管理标记丢失、指纹不一致、回读不确定、计划过期属于安全故障。

每日推荐和曲库整理的临时故障采用固定上限退避：5 分钟、30 分钟、2 小时；三次仍失败后等待下一个正常周期。重试状态持久化到现有任务计划中，包含失败次数、下次重试时间和原始计划槽位。成功后清除重试状态。智能歌单沿用现有按类型重试机制，只统一输出结构和健康状态。

任何重试都必须继续经过原有互斥锁、归属标记、指纹和回读校验，因此不会通过重试绕过安全边界或重复接管用户歌单。

## 二、事务化管理员会话

新增 `auth_session` 表，每行保存会话摘要、用户名、创建时间和过期时间。只保存 SHA-256 摘要，不保存浏览器令牌明文。表结构包含摘要主键和过期时间索引。

升级时在同一个数据库事务中：

1. 创建新表。
2. 将旧 `auth_sessions` JSON 中仍有效且结构正确的记录写入新表。
3. 写入迁移标记。
4. 保留旧键一个发布周期作为回退数据，但生产读取只使用新表。

创建会话、验证会话、退出当前会话、修改密码后撤销全部会话均使用单次数据库事务。最多保留 20 个最新有效会话；清理过期会话在创建和验证时执行，不需要额外后台线程。

现有 PBKDF2 参数、Cookie 名称、HttpOnly、SameSite、HTTPS Secure 判断和登录限流保持不变。

## 三、轻量状态与可观测性

### 状态接口

保留 `/api/status` 路径和现有前端依赖字段，避免页面同时大改，但将内部数据分成两层：

- 高频摘要：连接状态、当前任务、调度健康、托管数量、学习计数、最近运行和最近错误。
- 低频详情：完整诊断、每日推荐算法统计、较长运行记录和需要展开的核对信息。

`/api/status` 只返回高频摘要。现有页面确实需要的少量字段继续兼容；详细内容迁移到专用诊断接口，并只在相关页面可见或用户展开时加载。

### 学习统计

`BehaviorRepository` 新增聚合统计查询，在 SQLite 中计算总学习歌曲、偏好歌曲、冷却歌曲和最后更新时间，不再通过 `load_track_states()` 载入所有 JSON 后逐首计算。统计结果允许 10～15 秒进程内缓存；收到新的播放证据、清除学习数据或切换用户时立即失效。

状态页显示调度器：

- 正常：线程存活且心跳在合理时间内。
- 执行中：当前有自动任务。
- 重试中：存在已安排的临时故障重试。
- 异常：线程意外停止或心跳超时。

状态文案不得把调度异常显示成“空闲”。

## 四、前端样式治理

### 视觉基准

播放列表页面当前已经通过主题、播放器图标、表头对齐和全屏播放验证，作为全站视觉基准。保持以下原则：

- 主内容在左，次要设置和操作在右侧或下一层。
- 浅色、暖色、深色主题保持明确的左右区域层次。
- 默认控件为中性灰色，只有选中、播放和确认状态使用绿色。
- 不恢复大面积彩色按钮、粗体堆叠或无层次纯白背景。
- 图标和箭头只使用主题语义变量，不写死黑色或白色。

### CSS 边界

`product.css` 从“所有历史规则入口”收缩为基础布局和仍被所有页面共享的兼容入口。新边界为：

- 主题令牌和背景：现有 `theme-tokens.css`、`theme-background.css`。
- 通用控件：`ui-components.css` 和 `design-system.css`。
- 管理壳层：`management-shell.css`。
- 播放列表与播放器：现有播放列表专用文件。
- 设置、每日推荐、智能歌单、外部歌单：各自页面样式文件。

迁移以保持计算后样式不变为前提。先移动页面专属规则，再合并同一文件中的重复选择器，最后删除被更高优先级永久覆盖的旧规则。不得单纯把新修补继续追加到文件末尾。

所有页面继续在脚本执行前加载主题，避免首屏闪烁。每套主题验证普通页面、嵌入页面、窄屏、播放条和全屏播放。

## 五、后端模块边界与历史清理

`create_app()` 只负责组装依赖、中间件和路由模块。认证路由、状态路由以及仍留在入口中的曲库管理路由分别提取到聚焦模块；路由路径和响应兼容字段保持不变。

每日推荐不再通过导入时修改 `DailyMixin.daily_signature`。新增明确的策略/签名函数，由 `DailyMixin` 直接调用当前策略。旧版算法文件中仍被当前策略复用的纯函数保留并改为中性名称；只作为兼容导出的版本别名集中到一个模块，不再形成循环导入。

清理范围包括：

- 没有生产调用的 `Engine.scheduler()`。
- 只服务旧调度器的 `interval_minutes` 运行逻辑；读取旧数据仍容忍该字段。
- `web.py` 中未使用的导入。
- 能由新模块直接替代且测试证明无调用的版本包装文件或别名。

历史数据库字段不做破坏性删除。代码停止写入后仍允许旧数据库携带这些字段，保证降级与恢复不受影响。

## 六、测试策略

所有行为修改遵循测试先行。

### 自动任务

- `run_due()` 外围异常后，调度线程继续下一轮。
- 心跳、连续失败次数和最近错误正确更新。
- 关闭应用会停止并有限等待调度线程。
- 每日推荐和曲库整理临时错误按 5 分钟、30 分钟、2 小时重试。
- 第三次失败后进入下一正常周期。
- 安全错误不进入临时重试。
- 重启后能够从持久化重试状态继续。

### 会话

- 旧 JSON 会话无损迁移。
- 两个并发登录都保持有效。
- 登录与退出并发不会恢复已撤销会话。
- 修改密码原子撤销旧会话并建立新会话。
- 过期清理与 20 个会话上限正确。

### 性能与状态

- `/api/status` 不调用 `load_track_states()`。
- 大量学习状态下只执行聚合查询。
- 新证据和清除操作会使缓存失效。
- 调度器异常不能显示成空闲。
- 现有状态接口兼容字段继续存在。

### 前端

- Node 交互测试覆盖状态文案和按需加载。
- Playwright 验证三套主题的关键页面截图和计算样式。
- 播放列表表头、图标、展开箭头和全屏播放器保持现状。
- CSS 契约测试从检查某个历史文件字符串，升级为检查实际加载顺序和计算后样式；不通过删除断言来掩盖回归。

### 完整门禁

- Python 全量测试。
- Node 全量测试。
- Playwright 视觉和交互测试。
- Python 3.11、3.12 CI。
- Docker 构建、健康检查和升级副本测试。
- 部署前数据库备份和回滚验证。

## 七、实施顺序与发布

1. 调度监督、健康状态和重试策略。
2. 事务化会话及迁移。
3. 状态聚合和接口减负。
4. 后端模块拆分与明确的每日策略入口。
5. CSS 按页面迁移和重复规则清理。
6. 完整回归、预览部署、资源复测。

每一阶段保持独立提交和可运行状态。先在隔离工作树实现，完成后提供本地/预览环境供核对。用户确认预览后才能合并、发布 GitHub 版本、推送镜像和更新 TrueNAS 部署；设计确认本身不授权外部发布。

## 成功标准

- 调度器在注入一次异常后仍能执行后续周期，状态页可观察其健康。
- 临时故障不会让当日任务直接丢失，安全故障不会被自动重试掩盖。
- 并发会话测试无丢失更新。
- `/api/status` 不随已学习歌曲数量线性解码全部状态。
- 当前三套主题和已认可页面没有可见回归。
- `product.css` 的页面专属规则和重复覆盖显著减少。
- 生产资源占用不高于 2.0.8 的合理波动范围。
- 全部自动化测试、镜像健康检查和升级测试通过。
