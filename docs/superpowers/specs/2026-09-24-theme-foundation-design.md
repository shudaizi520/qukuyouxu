# 主题与管理界面基础层整理设计

日期：2026-09-24

## 1. 目标

在重新设计管理菜单与六个管理页面之前，先整理现有表现层，使所有页面只使用一套主题变量、图标状态和公共组件规则。

本阶段必须保持现有业务功能、页面内容、路由和交互行为不变。完成后，现有清爽浅色、暖色纸感、深色夜间三个主题在视觉上不应发生有意变化。

未来可增加十几个静态或动态外观。动态效果仅作用于背景，不驱动菜单、按钮、输入框或图标的持续动画。

用户随后明确要求解决图标在悬停、选中和危险状态下颜色不一致的问题。因此视觉保持的边界是：页面结构、内容、尺寸和业务交互不变；允许把暖色/夜间页面遗留的硬编码浅色表面，以及同一控件状态的冲突颜色，收敛到已确认的主题语义变量。所有这类差异必须由截图逐项审查，不能借此重新设计页面。

## 2. 当前问题

当前已有可复用的主题基础：

- `appearance.js` 负责保存、应用和跨 iframe 同步主题。
- `design-system.css` 已定义 `--app-*` 语义变量和三个现有主题。
- 六个管理页面使用 `management-shell.js` 生成统一导航。

需要整理的部分：

- `product.css` 与 `design-system.css` 同时控制全局颜色、控件和管理页面，存在职责重叠。
- 主题覆盖规则仍残留在 `product.css`，新增主题需要维护很长的选择器列表。
- 页面与附属样式中仍有大量直接颜色值，不能保证图标及状态在所有主题下一致。
- 主题元数据同时写在 `appearance.js` 与 `appearance.html`，新增主题容易遗漏其中一处。
- 各 HTML 页面引用的静态资源版本号不一致，可能造成部署后新旧样式混用。
- 当前没有可用的真实浏览器截图工具，结构测试通过不能证明视觉一致。

## 3. 范围

### 3.1 本阶段包含

- 整理主题语义变量。
- 统一按钮、菜单、输入框、图标、焦点、禁用和危险状态。
- 统一六个管理页面的导航壳层与资源加载顺序。
- 把主题选项元数据收敛为一个来源。
- 为未来静态壁纸和动态背景预留独立背景层。
- 增加防止直接颜色值、资源版本漂移和主题选项重复定义的自动检查。
- 建立真实浏览器视觉验收门槛。

### 3.2 本阶段不包含

- 不重新设计设置页面内容。
- 不调整六个管理页面的信息架构或功能顺序。
- 不新增正式主题。
- 不实现粒子、视频、动画渐变等动态背景。
- 不修改播放器、导入、整理、推荐、授权或后台任务逻辑。
- 不以新的覆盖规则继续叠加在旧规则末尾。

## 4. 采用方案

采用“定向整理表现层”，不进行整套前端重写。

保留现有 HTML、业务 JavaScript、接口和路由。把主题、公共组件、管理壳层和页面布局划分成明确的样式职责，并逐步移除已有重复规则。

不采用以下方案：

- 继续追加 CSS 覆盖：短期快，但会放大主题间的不一致。
- 全量重写前端：风险和验证成本过高，也会波及已稳定的业务功能。

## 5. 样式职责

最终表现层分为四个职责区域。实际文件可以在迁移中逐步落位，但每条规则只能属于一个区域。

### 5.1 主题变量

主题变量是颜色与背景参数的唯一来源，包含：

- 页面背景、侧栏、表面、控件、浮层和选中表面。
- 主文字、次要文字、反色文字和分隔线。
- 强调色、强调色悬停、强调色上的文字。
- 普通图标、弱化图标、悬停图标、选中图标和危险图标。
- 成功、警告、危险及其弱化背景。
- 焦点轮廓和阴影。
- 背景图片、背景遮罩、背景透明度与背景静止/动态类型的预留参数。

主题定义不得包含具体页面选择器。

### 5.2 公共组件

公共组件只消费语义变量，负责：

- 按钮、链接、输入框、选择框、开关。
- 菜单项、标签、状态提示、对话框。
- 图标的默认、悬停、选中、禁用和危险状态。
- 键盘焦点与无障碍状态。

所有 SVG 图标使用 `currentColor`。组件状态控制父元素的 `color`，不单独给 SVG 写悬停颜色。文本符号图标也必须继承同一套图标变量。

### 5.3 管理壳层

管理壳层只负责：

- 六个入口的顺序、当前页状态和键盘导航。
- 页面内容的最大宽度、左对齐方式和响应式边距。
- 嵌入播放页时与左侧歌单、顶部搜索和底部播放器的边界。
- 管理页面公共操作按钮的尺寸与排列。

壳层不能定义独立主题颜色，只能消费公共组件和主题变量。

### 5.4 页面布局

页面样式只负责该页面独有的网格、列表列宽和内容排列。不得重新定义共享按钮、图标、菜单、主题色或焦点状态。

## 6. 主题注册与应用

`appearance.js` 中保留一个主题注册表，作为主题标识、名称、色彩模式和背景类型的唯一元数据来源。外观页面的主题卡片由注册表生成，不再在 HTML 中手工复制主题清单。

每个主题至少包含：

- 稳定且不可随意变更的主题 ID。
- 显示名称。
- `light` 或 `dark` 色彩模式。
- `solid`、`image` 或 `dynamic` 背景类型。
- 是否包含运动效果。

颜色数值仍由 CSS 主题变量定义。注册表不在 JavaScript 中复制颜色，以避免运行时内联样式和 CSS 产生两套真相。

无效或已删除的主题 ID 自动回退到清爽浅色。主题切换继续写入本地存储，并同步到允许访问的嵌入页面。

## 7. 背景层

未来主题背景使用独立层，位于页面内容之后：

- `pointer-events: none`，不拦截任何点击、滚动或拖动。
- 不改变菜单、按钮、图标和表单的动画。
- 内容层通过主题表面与遮罩变量保证可读性。
- 嵌入管理页面时，动态背景只在最外层应用一次；iframe 内不重复播放。
- `prefers-reduced-motion: reduce` 时关闭持续动画并显示静态降级背景。
- 资源加载失败时回退到主题的纯色背景。
- 页面失焦或不可见时可暂停高成本动画。

本阶段只建立接口和静态占位，不加入正式动态效果。

## 8. 迁移策略

迁移按以下顺序进行，每一步都必须能独立验证和回退：

1. 为当前三个主题和关键组件建立结构、状态及视觉基线。
2. 补齐语义变量，建立图标状态契约。
3. 把 `product.css` 中的主题覆盖迁移到唯一主题层，并删除原规则。
4. 把共享按钮、菜单、输入框、焦点和图标规则迁移到公共组件层，并删除重复规则。
5. 统一 `management-shell.js` 与六个管理页面的资源引用和版本号。
6. 将外观页主题卡片改为由主题注册表生成。
7. 加入背景层接口及静态降级行为。
8. 完成三个现有主题的六页视觉回归后，才允许开始菜单与设置页面的重新设计。

迁移不是把旧规则留在原处再写更高优先级覆盖。每迁移一类规则，旧定义必须同时删除或明确限制到尚未迁移的旧页面。

## 9. 验证

### 9.1 自动检查

- 现有 Python 测试继续通过。
- 主题选择、持久化、无效主题回退和 iframe 同步行为测试。
- 管理导航六个入口、顺序和当前页状态测试。
- 所有管理页面以统一顺序加载表现层资源。
- 主题注册表与外观页展示一致，不保留第二份手写清单。
- 公共图标使用 `currentColor`，不出现页面级图标悬停颜色。
- 迁移后的主题和组件文件外，不允许新增未登记的直接颜色值。
- 静态资源版本统一，防止缓存混用。

### 9.2 真实浏览器视觉验收

完成声明之前必须使用真实浏览器，至少覆盖：

- 六个管理页面。
- 清爽浅色、暖色纸感、深色夜间三个主题。
- 1366×768 与 1920×1080 两个桌面视口。
- 默认、悬停、键盘焦点、选中、禁用和危险操作状态。
- 嵌入播放页时左侧歌单、顶部搜索和底部播放器均不被覆盖。

测试环境目前没有浏览器可执行文件。实施计划必须先解决可重复的截图工具；若无法建立真实浏览器验证，本阶段只能标记为“代码验证完成、视觉未验证”，不得宣称基础层已安全，也不得进入设置页面重设计。

## 10. 完成标准

满足以下全部条件，本阶段才算完成：

- 现有业务行为无变化。
- 三个现有主题的真实页面没有非预期视觉变化。
- 共享颜色、图标状态和组件状态只有一个定义来源。
- 六个管理页面共用同一管理壳层和资源加载顺序。
- 主题卡片由一个注册表驱动。
- 背景层不会阻断交互，并具备静态降级与减少动画策略。
- 自动测试通过，真实浏览器视觉矩阵完成。
- 没有以新补丁覆盖旧冲突规则。

完成该阶段后，再单独设计和实施管理菜单与设置页面，不在本阶段提前修改其视觉方案。
