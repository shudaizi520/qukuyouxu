# 多用户页面缓存设计

## 目标

在保留当前多 Plex 用户、服务器和音乐资料库隔离能力的前提下，减少管理页面重复进入时的等待和闪烁。用户返回近期访问的页面时，应先看到该 Plex 档案最近一次成功读取的数据，再由后台安静地确认是否有更新。

这项改动只优化浏览器端的只读数据复用，不改变后端业务数据、Plex 写入规则、任务调度或用户档案模型。

## 成功标准

1. 同一 Plex 档案近期访问过的管理页面再次打开时，不等待全部接口重新完成即可显示已有只读内容。
2. 任意时刻都不得把一个 Plex 档案的数据渲染到另一个档案的页面中。
3. 切换 Plex 档案时，当前画面立即进入该档案的独立加载状态；旧档案迟到的请求结果被丢弃。
4. 切回近期使用的档案时，可复用该档案自己的缓存。
5. 导入、整理、发布、删除、改名和设置变更只使受影响档案的相关缓存失效。
6. 后台任务进度、认证状态和其他实时状态继续从服务器读取，不显示缓存结果冒充实时结果。
7. 缓存有明确的容量和寿命上限，关闭浏览器标签页后全部释放，不增加 NAS 服务端常驻内存。

## 不做的事情

- 不保留多个常驻 iframe。
- 不把现有前端整体重写为 React 或其他框架。
- 不恢复未提交的表单、确认框、播放状态或危险操作上下文。
- 不缓存密码、Plex Token、授权二维码、音频、歌词、完整媒体文件或完整曲库目录。
- 不用缓存绕过后端的用户权限、档案状态或写前校验。
- 不改变当前 `X-Plex-Profile` 请求作用域和后端 `fixed_active` 隔离机制。

## 现状

主歌单页面使用一个 `playlistToolFrame` 加载管理页面。每次切换工具页都会重新设置 iframe 的 `src`，离开时页面 DOM、JavaScript 状态和已取得的数据全部销毁。再次进入页面会重新加载静态资源并重新请求接口。

当前多用户链路已经具备正确的基础隔离：

- 浏览器在 `sessionStorage` 保存当前 `profile_id`；
- 应用 API 请求通过 `X-Plex-Profile` 指定 Plex 档案；
- 后端在整次请求期间用 `ProfileRegistry.fixed_active()` 固定档案；
- 歌单页在切换档案时增加请求代次并清空旧画面；
- 封面缓存已经使用登录账户、档案、Plex 账户、服务器和音乐资料库组成的作用域。

新的页面缓存应扩展这套边界，而不是另建较弱的身份判断。

## 推荐架构

### 1. 顶层标签页缓存服务

在主歌单工作区创建一个小型内存缓存服务。嵌入的同源管理页面通过受控接口读取和更新缓存。缓存属于当前浏览器标签页；iframe 被替换时缓存仍在，标签页关闭后自动释放。

不使用多个 iframe 常驻，因为那会同时保留多套 DOM、事件监听器、轮询器和图片，增加内存及多用户切换风险。

### 2. 不可混淆的缓存作用域

缓存作用域由以下字段共同组成：

- 当前网页登录账户；
- Plex `profile_id`；
- Plex 账户 ID；
- Plex 服务器 `machineIdentifier`；
- Plex 音乐资料库 ID；
- 档案创建时间或等价的身份代次。

只有身份字段完整时才允许写入共享缓存。连接尚未完成、档案已停用或身份不完整时直接请求服务器，不建立可复用缓存。

缓存条目的完整键为：

`登录账户 + 档案作用域 + 规范化接口地址 + 表示版本`

缓存服务不根据页面标题、显示名称或当前全局活动档案推断身份。

### 3. 请求代次与迟到响应

每次切换档案、退出登录、停用档案或变更档案连接身份时，增加前端作用域代次。请求开始时捕获档案作用域和代次；响应返回时必须再次核对：

- 当前档案仍相同；
- 当前身份作用域仍相同；
- 请求代次仍有效；
- 发起请求的页面实例仍存在。

任何一项不一致，响应既不能渲染，也不能写入新作用域的缓存。能够取消的旧请求同时使用 `AbortController` 取消。

### 4. 先显示、后校验

缓存只用于适合复用的 GET JSON 数据，并采用三个状态：

- **新鲜**：直接显示；在短时间内不重复请求。
- **可复用但待确认**：立即显示缓存，同时在后台请求最新数据；成功后仅在内容发生变化时更新页面和缓存。
- **过期或不存在**：显示正常加载状态并请求服务器。

后台刷新失败时，页面可以继续显示已明确标注为旧数据的缓存，但不得把缓存状态描述成“刚刚同步”或“实时正常”。认证失败、档案不存在和权限错误必须立即撤下缓存画面并走现有错误处理。

### 5. 缓存范围

首批只缓存体积小、只读且重复进入成本明显的数据：

- 当前档案的歌单导航摘要；
- 智能歌单设置和摘要；
- 曲库整理的分类歌单摘要及最近一次只读结果；
- 导入来源列表和已导入歌单摘要；
- 系统设置中的非敏感展示数据；
- 外观设置。

以下数据不进入共享页面缓存：

- `/api/auth/*`；
- 后台任务运行状态、进度和轮询响应；
- Plex/QQ 授权流程；
- 搜索结果、完整歌曲明细、歌词、音频和媒体二进制；
- POST、PUT、PATCH、DELETE 的响应；
- 含 Token、Cookie 或其他凭据的数据。

允许列表由代码显式维护。未知接口默认不缓存。

### 6. 精准失效

缓存服务按“档案作用域 + 数据标签”失效，而不是全局清空。建议标签包括：

- `playlists`
- `library-summary`
- `smart-mixes`
- `external-sources`
- `settings`
- `appearance`

写操作成功后由现有操作点发送明确的失效标签。例如：

- 导入或更新歌单：当前档案的 `external-sources` 与 `playlists`；
- 发布、删除、改名或编辑歌单：当前档案的 `playlists` 和对应业务摘要；
- 完成曲库整理：当前档案的 `library-summary` 与 `playlists`；
- 更改智能歌单规则：当前档案的 `smart-mixes`；
- 改变连接身份、移除档案或退出登录：删除相应作用域的全部条目。

实时任务完成时也触发相同的精准失效，避免用户返回页面仍看到任务前结果。

### 7. 生命周期和内存上限

共享缓存只存在于顶层页面内存，不默认写入 `localStorage`。建议默认限制：

- 每个档案最多 16 个 JSON 条目；
- 整个标签页最多 48 个条目；
- 单条序列化后最大 512 KiB；
- 总估算容量最大 8 MiB；
- 最近最少使用条目优先淘汰；
- 普通摘要最大保留 15 分钟，可在 30～60 秒后后台确认；
- 设置和外观等低频数据最大保留 30 分钟；
- 任务状态完全不缓存。

这些限制只影响浏览器内存，不提高 NAS Python 服务的常驻内存。

## 页面集成

新增独立的缓存模块，负责作用域、条目状态、容量、淘汰、失效和请求去重。`auth.js` 继续负责给网络请求添加 `X-Plex-Profile`，但不自行决定哪些业务接口可缓存。

管理页通过统一的 `cachedJson()` 读取允许缓存的 GET 接口。它必须保留现有 `PCHAuth.request()` 的认证、档案恢复和错误语义。页面仍可使用自己的渲染函数，不需要改造成单页框架。

主工作区继续使用一个 iframe。iframe 的 HTML 和 JavaScript仍会重新初始化，但可立即取得当前档案的缓存 JSON，因此不会等待所有远端读取完成才出现内容。

## 错误和安全处理

- 缓存数据只作为同一身份作用域的旧快照，后端仍是唯一权威来源。
- 不在错误响应、未认证响应或部分响应上更新缓存。
- 档案切换期间不允许用上一个档案的数据充当占位内容。
- 缓存作用域无法验证时宁可重新加载，也不降级为仅使用 `profile_id`。
- 登出时清空所有内存缓存并取消未完成请求。
- 删除或停用档案时立即删除该档案全部缓存。
- 浏览器后退、iframe 消息和子页面自行切换档案都走同一套代次检查。

## 测试

### 单元测试

- 不同登录账户、档案、服务器或资料库永不命中同一条目。
- 新鲜、待确认和过期三种状态符合时间边界。
- 同一键的并发读取只发起一次网络请求。
- 切换档案后，旧请求不能渲染或写入新缓存。
- 写操作只失效当前档案指定标签。
- 登出、停用档案和连接身份变化清空正确作用域。
- LRU、单条容量、总容量和条目数量上限生效。

### 集成测试

- 用户 A 打开曲库整理，切到用户 B，再切回 A；两边只显示自己的内容，A 可快速恢复。
- 在 A 的请求未返回时切到 B；A 的迟到响应不会出现在 B 页面。
- A 发布或删除歌单后，A 的列表重新读取；B 的缓存保持不变。
- iframe 重新载入后可复用当前档案缓存，但未保存表单不会恢复。
- 后台任务页面始终显示实时结果，不使用旧任务状态。
- 现有封面、播放、喜欢状态、外部歌单和用户切换测试继续通过。

### 资源验证

在至少两个 Plex 档案间往返访问主要管理页面，记录浏览器缓存条目数、估算字节数和 NAS 容器内存。缓存达到上限后应稳定，不随切换次数持续增长；NAS 服务端空闲内存不应因浏览器缓存功能发生可测的持续增长。

## 发布方式

先只部署到 9513 预览环境。验证多用户往返、后台任务、导入、曲库整理和写后刷新均正确后，再由用户确认是否发布 GitHub 和更新 9512 正式环境。
