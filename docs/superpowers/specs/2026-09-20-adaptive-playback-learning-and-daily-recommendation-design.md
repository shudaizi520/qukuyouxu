# 自适应播放学习与每日推荐 V2 设计

日期：2026-09-20
状态：待用户审阅

## 1. 要解决的问题

现有播放学习依赖 Plex Webhook 中的停止位置和歌曲时长。真实环境里这些字段可能缺失，导致正常切歌没有形成负向证据；旧算法又以固定阈值和事件列表临时汇总为主，无法可靠区分误操作、近期听腻和长期不喜欢。

V2 的目标是：

- 普通切歌能够被识别，但一次误操作不会把歌曲判死。
- 反复跳过的歌曲会逐渐延长冷却，不再频繁出现。
- 后来重新完整听完时，歌曲能够恢复。
- 每个 Plex 用户和音乐资料库独立学习，绝不串数据。
- 每日推荐同时兼顾熟悉、新鲜、久未重听和跨口味探索。
- 优先复用 Plex Sonic Analysis 的声音相似结果，不自行扫描音频文件。
- 对约 3,000 首的家庭曲库保持低 CPU、低内存和低磁盘写入。
- 用户界面保持简单，不暴露需要用户理解的算法参数。

## 2. 总体方案

采用轻量的个人自适应推荐模型，不引入神经网络训练服务。系统分为三个独立部分：

1. **播放会话识别器**：把乱序、重复或字段不完整的 Plex Webhook 还原成可信的播放行为。
2. **偏好学习器**：分别维护长期喜好、近期疲劳、跳过置信度和个人跳歌基准。
3. **每日推荐器**：先执行硬性排除，再按互斥候选桶和个性化得分选出歌单。

Webhook 接收层只负责解析、去重和交给会话识别器。偏好学习与每日推荐不再直接耦合在 Webhook 文件中。

## 3. 播放行为识别

### 3.1 会话关联

会话按“配置档案、Plex 账户、服务器、播放器”隔离。一次播放至少记录歌曲、开始时间、最后事件、播放位置、歌曲时长、暂停区间和播放代次。

以下情况才确认一次切歌：

- 歌曲 A 停止后，同一账户和播放器在 30 秒内开始播放不同的歌曲 B；或
- 歌曲 A 仍被记录为活动播放时，同一账户和播放器直接开始歌曲 B。

停止后没有下一首、退出 Plex、断网、播放器消失和长时间暂停均不记负向。自然播放到结尾再自动播放下一首记为完成，不记跳过。同一歌曲重新播放不当作切歌。

### 3.2 播放比例

歌曲总时长按以下顺序取得：Webhook 有效时长、本配置档案的曲库缓存时长。两者都没有时，不产生负向证据。

有效播放时间优先使用可信的播放位置增量；字段缺失时使用开始到切换的活动时间，并扣除已知暂停时间。明显跳转进度的情况不能伪装成完整收听。

### 3.3 行为权重

确认切歌以后才使用以下规则：

| 行为 | 证据 |
|---|---:|
| 播放不足 20%，且活动时间不超过 60 秒 | 跳过证据 +0.45 |
| 播放不足 50% 的其他切歌 | 跳过证据 +0.30 |
| 播放 50% 至 80% 后切歌 | 近期疲劳 +0.10，不改变长期喜好 |
| 播放达到 80% | 正向证据 +0.75 |
| Plex 确认完整播放 | 正向证据 +1.00 |
| 收藏、明确喜欢或高评分 | 强正向 |
| 明确“不再推荐”或低评分 | 强负向，持续排除 |

同一播放代次最多写入一个最终学习结果。同一歌曲同一天的普通跳过证据最多累计 0.60，避免重复 Webhook 或播放器异常放大负向。

## 4. 个人自适应学习

### 4.1 两层记忆

- **长期喜好**用于判断一首歌总体是否符合用户口味。
- **近期疲劳**用于判断用户是否只是最近听腻，需要暂时少推。

正向证据按约 180 天半衰期衰减，普通跳过证据按约 60 天半衰期衰减，近期疲劳按约 7 天半衰期衰减。明确“不再推荐”不会自动失效。

### 4.2 个人跳歌基准

每个配置档案分别统计有效完成、早期跳过和普通跳过。少于 30 次有效结果时使用中性倍率 1.0；达到 30 次后，根据个人平均跳过率校准单次跳过权重：

`个人倍率 = 限制在 0.7 至 1.3 之间的 (1.25 - 个人跳过率)`

习惯频繁试听的人，单次跳过影响较弱；平时很少跳歌的人，早期跳过影响较强。跨日期反复跳过同一首歌仍会明显增加置信度。

### 4.3 动态冷却

衰减后的近期跳过证据映射为：

| 跳过证据 | 冷却 |
|---|---:|
| 少于 0.25 | 不冷却 |
| 0.25 至 0.60 | 1 天 |
| 0.60 至 1.20 | 7 天 |
| 1.20 至 2.00 | 30 天 |
| 2.00 至 3.00 | 90 天 |
| 3.00 及以上 | 180 天 |

一次完整播放会使普通跳过证据减半，并重新计算冷却；连续两次完整播放通常可恢复为正常候选。收藏或明确喜欢会清除普通跳过影响。明确“不再推荐”只有用户主动取消或改为喜欢时才恢复。

冷却结束后，歌曲先进入低概率恢复观察，不立即回到高频推荐。每日 50 首最多放入 2 首恢复观察歌曲；若再次早期跳过，冷却继续升级。

## 5. 每日推荐

### 5.1 先筛选，再排序

硬性排除项包括：

- 明确不推荐；
- 尚未结束冷却；
- 文件不可用或元数据不足；
- 同名同歌手的重复版本；
- 仍在防重复窗口内；
- 不属于当前用户和曲库。

硬性排除绝不为凑满 50 首而放宽。

### 5.2 互斥候选桶

每首歌只能进入一个桶，按以下优先顺序归类：

1. 新加入曲库或从未播放：新鲜发现。
2. 冷却结束并符合观察条件：恢复观察。
3. 有稳定长期正向：稳定偏好。
4. 与近期正向歌曲相似：近期口味。
5. 曾经喜欢但很久未听：久未重听。
6. 其他合格歌曲：跨口味探索。

默认 50 首目标配比为：

| 类型 | 数量 |
|---|---:|
| 稳定偏好 | 14 |
| 近期口味 | 8 |
| 新鲜发现 | 14 |
| 久未重听 | 8 |
| 跨口味探索 | 4 |
| 恢复观察 | 最多 2 |

某一桶不足时，名额按个性化得分转给其他非恢复桶。新鲜发现与跨口味探索合计默认 18 首，并根据最近至少 30 次发现类行为在 14 至 24 首之间自动调整：完整播放较多则提高，早期跳过较多则降低，但不会降为零。

### 5.3 排序与防重复

排序综合长期喜好概率、证据可信度、近期口味相似度、距离上次播放时间、疲劳、新鲜度和多样性。真正随机探索最多占歌单的 5%。

- 普通歌曲进入每日推荐后，21 天内不重复。
- 稳定喜欢歌曲也至少间隔 14 天。
- 昨日未播放歌曲最多保留 2 天，不能无限占位。
- 已播放或已跳过歌曲在下一次生成时优先替换。
- 同一歌手默认最多 2 首，同一专辑默认最多 1 首。
- 候选不足时先把专辑上限放宽到 2，再把歌手上限放宽到 3；硬性排除不放宽。
- 最终顺序再次打散，避免相邻歌曲属于同一歌手或同一类型。

## 6. Plex Sonic Analysis

Plex Sonic Analysis 正式作为可选增强信号纳入 V2。

- 系统继续通过 Plex 的 `nearest`/`similar` 能力取得声音相似曲目，不直接读取或扫描音乐文件。
- 自动检测是否存在有效声音相似结果，不增加用户开关。
- 有结果时，主要提升“新鲜发现”和“近期口味”中声音相近歌曲的排序。
- 用户真实完整播放、跳过、收藏和明确反馈始终优先于声音相似度。
- Sonic 不可用、尚未分析完成或接口失败时，自动退回歌手、专辑、类型、风格、心情和播放行为，不影响生成。
- 相似结果缓存 7 天，避免反复请求 Plex。

Plex 负责初次高 CPU 的声音分析；曲库有序不重复执行音频模型。用户可在 Plex 中把声音分析安排在维护时段，新加入歌曲由 Plex 增量处理。

## 7. 数据存储

现有 `state` 表继续保存设置、缓存和计划；行为数据改为同一个 SQLite 文件中的关系表，避免每次事件都重写整份 JSON。

### 7.1 原始行为表

`behavior_event` 每条一行，包含配置档案、曲目、行为类型、权重、时间、播放比例、播放器和播放代次。事件键唯一，防止重复写入；按配置档案与时间、配置档案与歌曲建立索引。

每个配置档案保留最近 180 天且最多 20,000 条，超出后删除最旧记录。只保存学习所需字段，不保存 Webhook 原始请求、令牌或密钥。

### 7.2 学习汇总表

`behavior_track_state` 每个“配置档案＋歌曲”一行，保存正向证据、跳过证据、疲劳、冷却和最近行为。`behavior_user_state` 每个配置档案一行，保存个人跳歌基准和推荐效果统计。

每次行为只追加一条事件并更新对应的一首歌，不扫描全部历史。每日生成时直接读取当前配置档案的汇总状态。

## 8. 升级与故障保护

迁移在事务中执行，并带版本标记，可重复运行：

- 保留用户、曲库、扫描缓存、现有歌单、自动任务和设置。
- 现有正向事件按原强度迁移。
- 现有普通负向按弱证据保守迁移。
- 旧 JSON 行为列表在迁移验证成功后保留一个版本周期，不立即删除。
- 任一配置档案迁移失败时，不启用该档案的 V2 推荐，也不修改其 Plex 歌单。
- V2 生成结果未通过数量、重复、隔离和硬性排除校验时，拒绝发布并保留当前歌单。
- Sonic 调用失败只触发降级，不会导致每日任务失败。

## 9. 界面

不增加算法设置页面。账户与成员页面继续使用每个配置档案的“播放学习”开关，新添加配置档案默认开启。

运行状态页只显示四项：

- 已学习；
- 偏好歌曲；
- 冷却中；
- 当前播放。

现有“负向歌曲”改为“冷却中”，避免把临时疲劳误解成永久讨厌。详细算法数据只进入诊断报告，不在主界面堆放小字。

## 10. 验证标准

自动测试必须覆盖：

- 不同时长和不同比例的切歌；
- 停止但没有下一首、退出、断网、暂停和拖动进度；
- 同播放器切换歌曲、同歌重播、Webhook 乱序与重复；
- Webhook 缺少时长时从曲库补齐；完全无法确认时不记负向；
- 单日负向上限、跨日重复、个人跳歌基准、证据衰减与恢复；
- 多用户、多曲库隔离和儿童曲库排除；
- 重启后的会话和学习状态；
- 互斥候选桶、配比、防重复、歌手/专辑上限和动态发现比例；
- Sonic 有结果、无结果、超时和错误降级；
- 从现有 1.1.9 数据迁移、重复迁移和回滚；
- 3,000 与 10,000 首模拟曲库的生成性能。

验收时必须确认：现有完整测试全部通过；新算法不会发布重复、跨用户、明确排除或冷却中的歌曲；数据库写入为单事件增量写入；关闭 Sonic 后仍可正常生成；现有 Plex 歌单和音乐文件不被破坏。

## 11. 不在本次范围内

- 不自行训练或运行音频神经网络。
- 不直接打开、修改或上传音乐文件。
- 不做跨家庭、跨用户的协同过滤。
- 不从 QQ 音乐或其他平台自动下载歌曲。
- 不让用户手动调整算法权重和阈值。

这些边界保证 V2 对个人 NAS 足够智能，同时保持可解释、低负载和可维护。
